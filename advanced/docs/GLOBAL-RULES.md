\## ۱. شناسنامه پروژه



| مورد | مقدار |

|------|-------|

| نام پروژه | \*\*FraudTransactionForge\*\* |

| نوع پروژه | سامانه‌ی مدیریت، تبدیل و ارسال پیام تراکنش به سرویس بیرونی |

| معماری | \*\*Frontend-only\*\* (کل منطق در سمت کلاینت؛ بک‌اند واقعی نداریم) |

| کاربر هدف | برنامه‌نویس، تستر، مدیر پروژه (کار با سامانه Fraud با داده‌های Fake) |

| تعداد نقش‌ها | \*\*بدون نقش/بدون احراز هویت\*\* — تک‌کاربره |



\### هدف اصلی (جریان کاری End-to-End)

1\. کاربر پیام تراکنش با فیلدهای \*\*خوانا\*\* را وارد / آپلود / ویرایش می‌کند (مثل `transaction.json`).

2\. سامانه آن را \*\*اعتبارسنجی\*\* می‌کند.

3\. بر اساس `mapping.json`، نام فیلدهای داخلی به \*\*کدهای مقصد (`"951"` تا `"1000"`)\*\* تبدیل می‌شود.

4\. `payload` نهایی به API مقصد (`POST /transaction`) ارسال می‌شود.

5\. درخواست، پاسخ، خطا و \*\*نسخه‌ی mapping\*\* برای \*\*audit\*\* ذخیره می‌شود.



\### مشکل کسب‌وکاری

تولید مقدار برای پارامترهای تراکنش؛ پارامترهای تراکنش مقداردار می‌شوند تا تست سامانه Fraud با داده‌های ساختگی امکان‌پذیر شود.

\## ۲. دستورالعمل کلی برای AI (در هر تسک لازم‌الاجرا)



1\. \*\*قبل از شروع کدنویسی، کل فایل تسک + این فایل + `OPEN-QUESTIONS.md` را بررسی کن.\*\*

2\. اگر بخشی مبهم یا ناقص است، \*\*ابتدا سؤال بپرس\*\* و کد نزن.

3\. \*\*بدون تأیید صریح کاربر، هیچ نیازمندی جدیدی اضافه نکن\*\* (No Scope Creep).

4\. اگر تصمیم‌گیری لازم است، \*\*ابتدا پیشنهاد خود را با دلیل ارائه بده\*\* و منتظر تأیید بمان.

5\. توسعه \*\*مرحله‌ای (Incremental)\*\* باشد؛ هر تسک یک مرحله‌ی مستقل و قابل اجرا.

6\. در پایان هر مرحله \*\*لیست فایل‌های ایجادشده / تغییرکرده\*\* را اعلام کن (با مسیر کامل).

7\. کد باید \*\*قابل اجرا\*\* باشد؛ \*\*هیچ کد ناقص، فرضی، `TODO` بدون پیاده‌سازی یا Pseudo-code\*\* تحویل نده.

8\. \*\*DRY\*\*: از تکرار کد جلوگیری کن؛ منطق مشترک به `shared/` منتقل شود.

9\. کامپوننت‌ها \*\*قابل استفاده مجدد (Reusable)\*\* و \*\*Presentational/Container جدا\*\* باشند.

10\. در صورت وجود چند راه‌حل، \*\*بهترین را با ذکر دلیل\*\* انتخاب کن.

11\. \*\*خطاها به‌صورت واضح مدیریت شوند\*\* (پیام فارسی، قابل‌فهم، بدون Stack Trace خام برای کاربر).

12\. رابط کاربری \*\*کاملاً Responsive\*\* باشد.

13\. ساختار پروژه \*\*قابل توسعه و نگهداری\*\* باشد.

14\. پس از هر مرحله، \*\*نحوه‌ی اجرا و تست دستی\*\* آن مرحله را توضیح بده.

15\. API واقعی نداریم → \*\*Mock API / داده آزمایشی\*\* ایجاد کن.

16\. تمام تصمیمات مهم معماری در \*\*`DECISIONS.md`\*\* ثبت شود (فرمت ADR کوتاه).

17\. \*\*هیچ رمز عبور، کلید API یا اطلاعات حساسی داخل کد نباشد\*\* → فقط `.env`.

18\. در پایان هر مرحله \*\*خلاصه‌ی کار انجام‌شده\*\* ارائه شود.

19\. \*\*هیچ کدی بدون کامنت نوشته نشود\*\* (جزئیات در بخش ۹ همین فایل).

\## ۶. ساختار پوشه‌ها (Locked Structure)



```

src/

├── app/                # App.tsx, router.tsx, providers.tsx, layouts/

├── features/           # transactions, mappings, payload, submissions, templates

├── shared/             # api, components/ui, hooks, lib, types, i18n

├── stores/             # workspace.store.ts

├── config/             # env.ts, app-config.ts

├── assets/

├── main.tsx

└── index.css

```



\### قواعد وابستگی (Dependency Rules)

\- `shared/` → \*\*نباید\*\* به `features/` وابسته باشد.

\- `features/A` → \*\*نباید\*\* مستقیماً از داخلی‌های `features/B` import کند؛ فقط از `index.ts` عمومی آن feature.

\- `app/` می‌تواند به همه وابسته باشد.

\- import ها با \*\*Path Alias\*\* انجام شود: `@/app`, `@/features`, `@/shared`, `@/stores`, `@/config`.



\### قواعد نام‌گذاری

| مورد | الگو | مثال |

|------|------|------|

| کامپوننت | `PascalCase.tsx` | `MappingTable.tsx` |

| هوک | `useCamelCase.ts` | `useTransactionEditor.ts` |

| ابزار/منطق | `kebab-case.ts` | `payload-builder.ts` |

| تایپ | `\*.types.ts` | `mapping.types.ts` |

| اسکیما | `\*.schema.ts` | `transaction.schema.ts` |

| تست | `\*.test.ts(x)` کنار فایل اصلی | `payload-builder.test.ts` |

| Zustand Store | `\*.store.ts` | `workspace.store.ts` |

\## ۷. قواعد TypeScript



\- `strict: true`، `noUncheckedIndexedAccess: true`، `noImplicitAny: true`

\- ⛔ \*\*استفاده از `any` ممنوع\*\* — در موارد ناگزیر از `unknown` + Type Guard استفاده شود.

\- ⛔ \*\*`@ts-ignore` ممنوع\*\* (در صورت اجبار: `@ts-expect-error` + کامنت دلیل).

\- تمام داده‌های ورودی خارجی (JSON آپلودی، پاسخ API، LocalStorage) \*\*باید با Zod پارس شوند\*\*، نه Type Assertion.

\- `type` برای شکل داده، `interface` برای قراردادهای قابل‌گسترش.

\- خروجی توابع عمومی همیشه \*\*Type صریح\*\* داشته باشد.

\- برای عملیات خطاپذیر از الگوی `Result<T, E>` استفاده شود:

&#x20; ```ts

&#x20; type Result<T, E = AppError> =

&#x20;   | { ok: true; data: T }

&#x20;   | { ok: false; error: E };

&#x20; ```

\## ۸. قواعد مدیریت خطا



1\. یک کلاس خطای مرکزی `AppError` در `shared/api/api-error.ts` با فیلدهای:

&#x20;  `code`, `messageFa`, `httpStatus?`, `details?`, `cause?`

2\. دسته‌بندی خطا: `VALIDATION` | `MAPPING` | `NETWORK` | `SERVER` | `STORAGE` | `UNKNOWN`

3\. هر خطا در UI با کامپوننت مشترک `ErrorAlert` نمایش داده شود.

4\. خطاهای فرم → زیر همان فیلد + Focus خودکار روی اولین فیلد خطادار.

5\. ⛔ هیچ `catch {}` خالی مجاز نیست.

6\. ⛔ نمایش `error.stack` یا متن انگلیسی خام به کاربر ممنوع؛ متن فارسی + کد خطا برای پیگیری.

7\. `ErrorBoundary` سراسری در `app/providers.tsx` با دکمه‌ی «بازیابی».

\## ۹. قواعد کامنت‌نویسی (الزامی — «کد بی‌کامنت ننویس»)



\- هر فایل: \*\*File Header\*\* شامل هدف فایل و جایگاه آن در معماری.

\- هر تابع/هوک/کامپوننت عمومی: \*\*JSDoc فارسی\*\* شامل `@param`, `@returns`, `@throws` و در صورت وجود `@example`.

\- هر منطق کسب‌وکاری غیربدیهی: کامنت \*\*«چرا»\*\* (نه «چه»).

\- هر قاعده‌ی Mapping / تبدیل مقدار: کامنت با ارجاع به کد مقصد مربوطه.

\- کامنت‌ها \*\*فارسی\*\* باشند؛ نام متغیرها و کد \*\*انگلیسی\*\*.

\- ⛔ کامنت‌های بی‌ارزش مثل `// set state` ممنوع.

\## ۱۰. قواعد امنیت و محیط



\- تمام تنظیمات محیطی در `.env` با پیشوند `VITE\_`:

&#x20; ```

&#x20; VITE\_API\_BASE\_URL=

&#x20; VITE\_TRANSACTION\_ENDPOINT=/transaction

&#x20; VITE\_USE\_MOCK\_API=true

&#x20; VITE\_REQUEST\_TIMEOUT\_MS=15000

&#x20; VITE\_APP\_ENV=development

&#x20; ```

\- فایل `.env.example` نگه‌داری و کامیت شود؛ `.env` در `.gitignore`.

\- خواندن env \*\*فقط\*\* از طریق `config/env.ts` که ورودی‌ها را با Zod اعتبارسنجی می‌کند و در Fail-Fast خطا می‌دهد.

\- ⛔ Hard-code کردن URL، Token، کلید یا Header حساس در کد ممنوع.

\- داده‌های تراکنش \*\*Fake\*\* هستند؛ اما در لاگ‌های Audit، شماره کارت/حساب باید \*\*Mask\*\* شود (`6037\*\*\*\*1234`).

\## ۱۱. قواعد Accessibility (a11y)



\- تمام فیلدها `<label>` مرتبط با `htmlFor` داشته باشند.

\- عناصر تعاملی با \*\*Keyboard\*\* قابل استفاده باشند (`Tab`, `Enter`, `Esc`, `Space`).

\- Dialog ها: `role="dialog"`, `aria-modal="true"`, Focus Trap، بازگشت Focus پس از بستن.

\- خطاها با `aria-invalid` + `aria-describedby` به فیلد متصل شوند.

\- کنتراست حداقل \*\*WCAG AA (4.5:1)\*\* در هر دو تم.

\- ⛔ انتقال معنا فقط با رنگ ممنوع (همراه آیکون/متن).



\---



\## ۱۲. قواعد تست



\- هر تسکِ حاوی منطق (Engine، Validator، Normalizer، Store، Hook) \*\*باید تست Vitest\*\* داشته باشد.

\- حداقل پوشش برای پوشه‌های منطقی: \*\*`features/mappings/engine` ≥ 90%\*\*، سایر منطق‌ها ≥ 70%.

\- Naming تست: `describe('<unit>')` → `it('باید ... کند')` (فارسی).

\- هر تست باید حالت‌های \*\*Happy Path + Edge Case + Error Case\*\* را بپوشاند.

\- ⛔ تست وابسته به شبکه‌ی واقعی ممنوع (Mock الزامی).

\## ۱۳. تعریف «Done» (Definition of Done) — برای تمام تسک‌ها



یک تسک تنها زمانی Done است که \*\*همه‌ی\*\* موارد زیر برقرار باشد:



\- \[ ] `npm run dev` بدون خطا اجرا می‌شود.

\- \[ ] `npm run build` بدون خطا و بدون Warning تایپ کامل می‌شود.

\- \[ ] `npx tsc --noEmit` بدون خطا.

\- \[ ] `npm run lint` بدون Error.

\- \[ ] `npm run test` سبز است.

\- \[ ] در هر ۶ Breakpoint بررسی شده.

\- \[ ] در تم روشن و تاریک بررسی شده.

\- \[ ] در حالت RTL درست است (بدون چیدمان معکوس/شکسته).

\- \[ ] تمام فایل‌های جدید/تغییریافته با مسیر کامل اعلام شده‌اند.

\- \[ ] کامنت‌ها طبق بخش ۹ نوشته شده‌اند.

\- \[ ] تصمیمات معماری در `DECISIONS.md` ثبت شده‌اند.

\- \[ ] خلاصه‌ی کار + راهنمای تست دستی ارائه شده است.
