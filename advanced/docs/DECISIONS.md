# تصمیمات معماری — FraudTransactionForge

## ADR-001 — انتخاب Vite برای اسکلت پروژه

- وضعیت: پذیرفته‌شده
- تصمیم: پروژه با Vite، React و TypeScript راه‌اندازی می‌شود.
- دلیل: Vite برای توسعه Frontend-only سریع، ساده و سازگار با ساختار مرحله‌ای پروژه است.

## ADR-002 — ساختار Feature-Based

- وضعیت: پذیرفته‌شده
- تصمیم: کدها در لایه‌های `app`, `features`, `shared`, `stores`, `config` سازمان‌دهی می‌شوند.
- دلیل: این ساختار مرزبندی وابستگی‌ها را شفاف می‌کند و توسعه مرحله‌ای تسک‌ها را قابل نگهداری نگه می‌دارد.

## ADR-003 — اعتبارسنجی Fail-Fast برای env

- وضعیت: پذیرفته‌شده
- تصمیم: متغیرهای محیطی فقط از `src/config/env.ts` و با Zod خوانده می‌شوند.
- دلیل: اجرای برنامه با تنظیمات ناقص یا نامعتبر باید در همان شروع با پیام فارسی واضح متوقف شود.

## ADR-004 — Design Tokens با CSS Variables

- وضعیت: پذیرفته‌شده
- تصمیم: رنگ‌ها، سطح‌ها، شعاع و سایه‌های پایه با CSS Variables تعریف می‌شوند و Tailwind فقط به آن‌ها ارجاع می‌دهد.
- دلیل: تغییر تم روشن/تاریک بدون تکرار کلاس‌ها انجام می‌شود و قانون ممنوعیت رنگ Hard-code در کامپوننت‌ها رعایت می‌شود.

## ADR-005 — Self-host کردن فونت Vazirmatn

- وضعیت: پذیرفته‌شده
- تصمیم: فایل‌های `woff2` فونت Vazirmatn در `src/assets/fonts` نگه‌داری و با `font-display: swap` بارگذاری می‌شوند.
- دلیل: برنامه باید بدون CDN و به‌صورت Offline اجرا شود و وابستگی حریم خصوصی به سرویس خارجی نداشته باشد.

## ADR-006 — قاعده ارقام UI و Payload

- وضعیت: پذیرفته‌شده
- تصمیم: اعداد نمایشی با ابزارهای `toPersianDigits` و `formatToman` فارسی می‌شوند و داده‌های ساختاریافته با `toLatinDigits` لاتین می‌مانند.
- دلیل: UI برای کاربر فارسی خواناست، اما Payload و JSON با سرویس مقصد سازگار و قابل پردازش باقی می‌مانند.

## ADR-007 — JsonCodeEditor داخلی

- وضعیت: پذیرفته‌شده
- تصمیم: ادیتور JSON با `textarea`، شماره خط و دکمه Format داخلی پیاده‌سازی می‌شود.
- دلیل: تسک 03 افزودن CodeMirror یا کتابخانه مشابه را بدون تأیید ممنوع کرده و راهکار داخلی حجم و وابستگی را کاهش می‌دهد.

## ADR-008 — Select بومی مرورگر

- وضعیت: پذیرفته‌شده
- تصمیم: کامپوننت `Select` بر پایه عنصر native `select` ساخته می‌شود.
- دلیل: select بومی دسترس‌پذیری و رفتار کیبورد قابل اتکاتری دارد و نیاز به وابستگی خارجی را حذف می‌کند.

## ADR-009 — Routing مرکزی با React Router و Lazy Loading

- وضعیت: پذیرفته‌شده
- تصمیم: مسیرها در `src/app/router.tsx` با `createBrowserRouter` تعریف و صفحات با `React.lazy` بارگذاری می‌شوند.
- دلیل: نقشه مسیرها متمرکز، توسعه صفحات مرحله‌ای ساده، و Code Splitting برای کاهش بار اولیه فعال می‌شود.

## ADR-010 — سیاست پیش‌فرض TanStack Query

- وضعیت: پذیرفته‌شده
- تصمیم: `QueryClient` با `retry: 1`، `staleTime: 30_000` و `refetchOnWindowFocus: false` ساخته می‌شود.
- دلیل: رفتار داده‌های سمت کلاینت قابل پیش‌بینی می‌ماند و از درخواست‌های ناخواسته هنگام فوکوس پنجره جلوگیری می‌شود.

## ADR-011 — قرارداد Zod-First برای داده‌های دامنه

- وضعیت: پذیرفته‌شده
- تصمیم: تایپ‌های تراکنش، Mapping، Payload، Submission و Template از Schemaهای Zod با `z.infer` مشتق می‌شوند.
- دلیل: ورودی‌های خارجی مانند JSON کاربر و داده‌های ذخیره‌شده بدون Type Assertion اعتبارسنجی می‌شوند و Drift بین تایپ و Runtime رخ نمی‌دهد.

## ADR-012 — ساختار واقعی transaction.json

- وضعیت: پذیرفته‌شده
- تصمیم: قرارداد تراکنش مطابق نمونه واقعی `docs/transaction.json` با wrapper `mainTransaction` و آرایه `attrsList` تعریف می‌شود.
- دلیل: کاربر Q2 را با ارجاع به فایل واقعی پاسخ داده و جریان API نیز در `curl.txt` همین ساختار پوششی را نشان می‌دهد.

## ADR-013 — نسخه‌گذاری Mapping خارج از محتوای فایل

- وضعیت: پذیرفته‌شده
- تصمیم: محتوای Mapping همان object خام `code -> sourceField` می‌ماند و نسخه/metadata فقط در جدول دیتابیس، Repository و Audit نگهداری می‌شود.
- دلیل: فایل واقعی `docs/mapping.json` باید بدون تغییر ساختاری حفظ شود، اما ذخیره‌سازی محلی همچنان برای فعال‌سازی و Audit به version نیاز دارد.

## ADR-014 — قرارداد Payload پوششی

- وضعیت: پذیرفته‌شده
- تصمیم: Payload مقصد به شکل `mainTransaction.attrsList` باقی می‌ماند و فقط کلیدهای هر Leg به کدهای `951` تا `1000` تبدیل می‌شوند.
- دلیل: نمونه `curl.txt` ساختار پوششی را نشان می‌دهد و Q4 پاسخ API را به همان نمونه ارجاع داده است.

## ADR-015 — سیاست فیلدهای بدون مقدار

- وضعیت: پذیرفته‌شده
- تصمیم: مقدار پیش‌فرض فیلدهای بدون مقدار در Mapping برابر رشته خالی `""` است.
- دلیل: کاربر در Q5 صراحتاً اعلام کرده فیلدهای بدون مقدار باید با مقدار `""` ارسال شوند.

## ADR-016 — SQLite-WASM با sql.js برای ذخیره‌سازی محلی

- وضعیت: پذیرفته‌شده
- تصمیم: دیتابیس محلی با `sql.js` به‌صورت SQLite-WASM در مرورگر اجرا می‌شود و فایل دیتابیس در IndexedDB نگهداری می‌شود.
- دلیل: Q1 استفاده از SQLite-WASM در سمت مرورگر را تأیید کرده و این انتخاب با معماری Frontend-only، اجرای آفلاین و نیاز Audit پایدار سازگار است.
- محدودیت: در محیط تست Node/Vitest مسیر فایل WASM از مسیر فایل ماژول محاسبه می‌شود تا به ریشه درایو وابسته نباشد.

## ADR-017 — Repositoryهای Zod-First و Prepared Statement

- وضعیت: پذیرفته‌شده
- تصمیم: دسترسی به جدول‌های `mappings`، `templates` و `submissions` فقط از طریق Repositoryهای `shared/db` انجام می‌شود؛ ورودی و خروجی با Zod اعتبارسنجی و Queryها با Prepared Statement اجرا می‌شوند.
- دلیل: داده ذخیره‌شده قابل اعتماد فرض نمی‌شود و برای جلوگیری از SQL Injection و Drift بین مدل دامنه و دیتابیس، مرز ذخیره‌سازی باید اعتبارسنجی‌شده و متمرکز باشد.
- محدودیت: Export/Import در تسک 06 به helperهای فایل SQLite محدود است و اتصال UI تنظیمات در تسک‌های بعدی انجام می‌شود.

## ADR-018 — قرارداد خام Mapping مطابق docs/mapping.json

- وضعیت: پذیرفته‌شده
- تصمیم: فایل `src/features/mappings/data/default-mapping.json` دقیقاً همان شکل `docs/mapping.json` را دارد: یک object ساده از `code -> sourceField` بدون `version`، `fields` یا metadata اضافه.
- دلیل: کاربر قبل از شروع تسک 7 تأکید کرد فایل Mapping باید دقیقاً شبیه فایل `docs/mapping.json` باشد؛ نسخه Mapping فقط در دیتابیس و Audit نگهداری می‌شود، نه داخل محتوای Mapping.
- محدودیت: فاصله‌ها و نام فیلدها، از جمله مقدارهایی مثل `TrxBranchCode `، عمداً trim نمی‌شوند تا قرارداد فایل اصلی حفظ شود.

## ADR-019 — تفکیک Zustand از داده‌های پایدار/سروری

- وضعیت: پذیرفته‌شده
- تصمیم: Zustand فقط پیش‌نویس تراکنش، Mapping فعال، Payload مشتق‌شده، وضعیت اعتبارسنجی و dirty state را نگه می‌دارد؛ persist فقط روی `draftTransaction` و `isDirty` با کلید `ftf:workspace` فعال است.
- دلیل: داده‌های DB/API باید در Repository و TanStack Query بمانند و Store فقط وضعیت کاری کاربر را مدیریت کند.
- محدودیت: Payload و validation persist نمی‌شوند چون مشتق‌شده‌اند و بعد از تغییر تراکنش یا Mapping دوباره ساخته می‌شوند.

## ADR-020 — قرارداد دقیق JSON تراکنش در ادیتور

- وضعیت: پذیرفته‌شده
- تصمیم: JSON واردشده یا pasteشده توسط کاربر فقط وقتی پذیرفته می‌شود که دقیقاً ساختار `docs/transaction.json` را داشته باشد: wrapper `mainTransaction` با کلیدهای `fraudMessageId`، `sysName`، `businessId` و آرایه `attrsList`.
- دلیل: کاربر پیش از شروع تسک 08 تأکید کرد ساختار JSON باید دقیقاً شبیه `docs/transaction.json` باشد؛ بنابراین `parseTransactionJson` با Zod ورودی را قبل از ورود به Store رد/قبول می‌کند.
- محدودیت: ویرایش Attribute فقط روی اعضای `mainTransaction.attrsList` انجام می‌شود و wrapper اصلی تغییر شکل نمی‌دهد؛ تقویم شمسی بدون کتابخانه جدید و فقط با اعتبارسنجی دستی الگو/بازه روز و ماه کنترل می‌شود.

## ADR-021 — Import/Export دقیق transaction.json

- وضعیت: پذیرفته‌شده
- تصمیم: Import و Export تراکنش فقط با قرارداد wrapper `mainTransaction` و آرایه `attrsList` انجام می‌شود و همان خروجی Export باید بدون تغییر دوباره Import شود.
- دلیل: تسک 09 و تأکید کاربر در تسک 08 ساختار دقیق `docs/transaction.json` را الزام کرده‌اند؛ بنابراین مسیر فایل، Drag & Drop و paste همگی از `safeJsonParse` و `parseTransactionJson` عبور می‌کنند.
- محدودیت: Import جزئی فقط `attrsList` را جایگزین می‌کند و header فعلی را نگه می‌دارد؛ گزینه حذف فیلدهای خالی فقط در Export اعمال می‌شود و داده Store را تغییر نمی‌دهد.

## ADR-022 — مدیریت UI Mapping با حفظ قرارداد خام docs/mapping.json

- وضعیت: پذیرفته‌شده
- تصمیم: صفحه مدیریت Mapping فقط object خام `code -> sourceField` را ویرایش، Import و نسخه‌گذاری می‌کند و هیچ `version`، `fields`، `required`، `transform` یا metadata دیگری داخل محتوای Mapping ذخیره نمی‌شود.
- دلیل: کاربر پیش از تسک 7 تأکید کرد فایل Mapping باید دقیقاً شبیه `docs/mapping.json` باشد؛ بنابراین metadata نمایشی مثل برچسب فارسی، required و transform فقط از روی کد/UI مشتق می‌شود و در دیتابیس کنار نسخه ذخیره می‌شود، نه داخل JSON Mapping.
- محدودیت: Virtualization بدون کتابخانه جدید اضافه نشد و برای جدول از صفحه‌بندی استفاده شد؛ حذف نسخه‌های استفاده‌شده در Audit همچنان توسط Repository مسدود می‌شود.

## ADR-023 — موتور Pure برای Mapping و Payload Builder

- وضعیت: پذیرفته‌شده
- تصمیم: منطق تبدیل `Transaction + Mapping` به Payload در `src/features/mappings/engine` به‌صورت Pure و جدا از React، Store و I/O پیاده‌سازی می‌شود و Store فقط آن را فراخوانی می‌کند.
- دلیل: قلب تبدیل باید قابل تست، deterministic و قابل استفاده مجدد بماند؛ بنابراین مسیر خطا با `Result` برمی‌گردد و هیچ `throw` کنترلی داخل Engine استفاده نمی‌شود.
- تصمیم: Transformerها در یک Registry تایپ‌شده نگهداری می‌شوند تا افزودن transform جدید بدون تغییر Builder و مطابق اصل Open/Closed انجام شود.
- تصمیم: فایل Mapping خام دقیقاً به شکل `docs/mapping.json` حفظ می‌شود و metadata اجرایی مانند required، label، default و transform در `field-metadata.ts` از روی نام فیلد مشتق می‌شود.
- تصمیم: طبق پاسخ Q5، فیلدهای بدون مقدار با `""` وارد Payload می‌شوند؛ طبق Q8، تبدیل تاریخ شمسی به ISO در transform مستقل `jalaliToIso` آماده است و فقط در صورت تنظیم metadata برای فیلد مربوط اعمال می‌شود.

## ADR-024 — پیش‌نمایش Payload بدون ارسال شبکه

- وضعیت: پذیرفته‌شده
- تصمیم: پیش‌نمایش Payload با hook خواندنی `usePayloadPreview` و فراخوانی مستقیم موتور Mapping ساخته می‌شود و برای نمایش زنده، Store را mutate نمی‌کند.
- دلیل: کاربر باید قبل از ارسال دقیقاً خروجی، منشأ مقدارها، حذف‌شده‌ها و هشدارها را ببیند؛ نوشتن در Store فقط با اکشن صریح `buildPayload` انجام می‌شود.
- تصمیم: Diff، محاسبه حجم، mask مقادیر حساس و ساخت cURL در `payload-formatter.ts` به‌صورت Pure و بدون کتابخانه خارجی پیاده‌سازی می‌شود.
- تصمیم: cURL کپی‌شده همیشه از `<TOKEN>` placeholder استفاده می‌کند و هیچ Token واقعی یا داده احراز هویت در کد یا خروجی قرار نمی‌گیرد.
- محدودیت: دکمه ارسال واقعی در این تسک شبکه را صدا نمی‌زند و اتصال HTTP/Submission طبق نقشه پروژه به تسک‌های ۱۳ و ۱۴ موکول می‌شود.

## ADR-025 — HTTP Client با Fetch و Mock Adapter داخلی

- وضعیت: پذیرفته‌شده
- تصمیم: ارتباط شبکه فقط از طریق Wrapper داخلی `http-client.ts` روی Fetch API انجام می‌شود و axios یا کتابخانه جدید اضافه نمی‌شود.
- دلیل: Stack پروژه Fetch API را قفل کرده و Wrapper امکان Timeout، Retry، `X-Request-Id`، Zod validation و تبدیل خطا به `AppError` فارسی را یکپارچه می‌کند.
- تصمیم: Retry فقط برای خطاهای شبکه و پاسخ‌های `5xx`، حداکثر یک بار و با backoff کوتاه انجام می‌شود؛ پاسخ‌های `4xx` خطای اعتبارسنجی محسوب می‌شوند و retry نمی‌شوند.
- تصمیم: Mock API با Adapter داخلی در `shared/api/mock` پیاده‌سازی می‌شود و به‌جای MSW از همان مسیر `http-client` پاسخ می‌دهد.
- دلیل: API واقعی در دسترس نیست و افزودن MSW طبق قوانین پروژه نیازمند تأیید کتابخانه جدید بود؛ Adapter داخلی سناریوهای success، validation-error، server-error، timeout، network-error و slow را پوشش می‌دهد.
- تصمیم: Token فقط از env اختیاری `VITE_API_TOKEN` خوانده می‌شود و در صورت خالی بودن، Header احراز هویت ساخته نمی‌شود.

## ADR-028 — زیرساخت تست متمرکز و مرز shared برای Mapping

- وضعیت: پذیرفته‌شده
- تصمیم: زیرساخت تست در `src/test` شامل setup مشترک، factory داده دامنه، render helper و دیتابیس SQLite درون‌حافظه‌ای متمرکز شد.
- دلیل: تست‌های واحد، کامپوننتی و یکپارچه باید بدون شبکه واقعی و بدون وابستگی به IndexedDB مرورگر واقعی پایدار اجرا شوند.
- تصمیم: سناریوهای یکپارچه Import، Payload، ارسال موفق، خطای سرور، timeout، Template، Replay و نسخه Mapping در `src/test/integration/end-to-end-flow.test.ts` پوشش داده شدند.
- تصمیم: تست‌های معماری در `src/test/architecture/dependency-rules.test.ts` مرزهای engine، shared، ممنوعیت `any`/`@ts-ignore` و ممنوعیت رنگ hex خارج از `index.css` را کنترل می‌کنند.
- تصمیم: Schema، تایپ و مقدار پیش‌فرض Mapping به `shared` منتقل شد و Feature Mapping آن را re-export می‌کند تا `shared/db` به `features` وابسته نباشد.
- محدودیت: Thresholdهای coverage در `vitest.config.ts` ثبت شد، اما اجرای `npm run test:coverage` به نصب provider رسمی `@vitest/coverage-v8` نیاز دارد و طبق قانون پروژه بدون تأیید کاربر dependency جدید اضافه نشد.

## ADR-029 — آماده‌سازی تحویل، a11y و مستندات نهایی

- وضعیت: پذیرفته‌شده
- تصمیم: مسیر `/__ui` فقط در حالت توسعه فعال می‌ماند و در build تولیدی از ناوبری و route حذف می‌شود.
- دلیل: صفحه پیش‌نمایش UI ابزار داخلی توسعه است و نباید در نسخه تحویل production در دسترس کاربر نهایی باشد.
- تصمیم: Skip Link سراسری به `main-content` اضافه شد تا پیمایش کیبوردی سریع‌تر و قابل پیش‌بینی باشد.
- تصمیم: برای رفع هشدار chunk cycle در build، ماژول‌های workspace-domain در یک manual chunk مشترک قرار گرفتند و قانون import عمومی Feature حفظ شد.
- تصمیم: مستندات نهایی شامل README، راهنمای کاربر، قرارداد API، مرجع Mapping، عیب‌یابی و CHANGELOG اضافه شد.
- محدودیت: ممیزی Lighthouse و NVDA نیازمند اجرای دستی در مرورگر واقعی است؛ در این محیط با typecheck، lint، test، build و ممیزی متنی جایگزین اعتبارسنجی شد.
